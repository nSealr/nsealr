# Public-event review contract — P01 candidate

This is the semantic oracle for PROD-05/06, subject to independent P01 review. It does not replace target bounds or executable renderer fixtures. The Nostr source pin is `37db639582d857e12468dcccd99b2c7f1d657da9`; reviewed NIP-01/02/09/10/18/25/65 define network semantics. The stricter rejection/display choices below are explicit nSealr product decisions.

## Common structure and presentation

The new event-template contract accepts exactly `kind`, `created_at`, `content`, `tags`. Kind and time must satisfy the selected NIP-01 integer rules; strings and all aggregate counts/bytes must fit the versioned profile manifest. Missing, duplicate or unknown top-level template members reject. The engine selects `pubkey` and produces `id` and `sig`; callers cannot override them. A transport envelope or legacy adapter has a separately versioned schema and must normalize/validate before entering this contract.

Tags remain ordered arrays of strings. An empty tag or empty tag identifier rejects in the first product. Preserve order, duplicate tags and every string exactly in canonical signed bytes; do not silently normalize URLs, Unicode, IDs or whitespace. Interpretation may label a parsed value but never rewrites the signed value. Any transformation needs a new review. Duplicate JSON object members, including escaped equivalents, reject before semantic interpretation.

The review has an operation overview and complete indexed fields. Display the selected full public key, exact timestamp, kind, content and every tag/field; wrapping/pagination is bounded and no hidden suffix is accepted. Escape controls/bidi/confusable sequences as necessary to distinguish bytes/characters honestly; preserve the original canonical value. No remote image, HTML/Markdown execution or network fetch is part of review. URLs and host-supplied names are unverified text.

Two tag classes are allowed within a supported kind:

1. **Interpreted fields** have the kind-specific rules below. Malformed known tags, contradictory context or unsupported recognized semantics reject. Never relabel them as unknown to bypass validation.
2. **Uninterpreted fields** are shown completely in a visibly distinct “additional signed data — meaning not verified” area, with indexes, exact tag identifier and all strings. This does not assert a semantic effect or authenticate its origin. Their presence must be explicit before final consent. If the target cannot present them completely within its qualified limits, reject the request. Unknown kinds and opaque encrypted operations never enter this path.

Extra suffix strings in an otherwise recognized tag are additional uninterpreted fields only if they do not contradict the defined prefix; show them adjacent to that tag and mark the extension. A parser cannot discard them. K01 fixtures must include unknown tags and known-tag extensions, as well as a malformed known prefix that cannot fall back to raw display.

This permits publishing inspectable additional data in a known public-event operation. It does not imply arbitrary smart-contract execution, arbitrary Nostr kinds, recipient verification, payment authorization or a generic “sign bytes” command.

## Kind-specific matrix

| Kind | Interpreted content / tags | Deterministic behavior |
| --- | --- | --- |
| 0 | `content` is one JSON object with unique string member names. No network-verified profile identity is implied. Tags use the complete uninterpreted presentation. | Show every key/value with its JSON type and full nested structure; reject invalid/duplicate JSON or a value the renderer cannot represent completely. Known names may receive labels but gain no authentication. State that this replaces profile metadata. |
| 1 | `content` is plain text. Interpret `e` event references and their NIP-10 root/reply context, `p` public-key references and `q` event-ID/address quote references. Other tags use complete uninterpreted presentation. | Validate reference shapes. Recognize current `root`/`reply` markers; reject malformed/contradictory marked context. Unmarked `e` references are shown as references with explicit ambiguous reply context, never a guessed root/reply label. Show quote/mention targets without claiming their content/author verified unless matching signed evidence is checked. Non-kind-1 reply workflows are unsupported. |
| 3 | Interpret `p` entries as the entire submitted follow list, including supplied relay/name strings as unverified hints. Other tags and content use complete uninterpreted presentation. | Validate public-key reference shapes; show every entry and every additional field. Explain full-list replacement. Empty list is an explicit unfollow-all operation. Do not present an add/remove diff without verified prior state and freshness. |
| 5 | Interpret `e` event IDs, `a` addresses and `k` kind hints. Content is the deletion reason. Other tags use complete uninterpreted presentation. | Require at least one `e` or `a`. Parse an address as kind/public-key/remainder identifier without dropping colons in the identifier. Show every target and kind hint; do not claim target ownership from unverified references. Address deletion can cover earlier versions up to the request timestamp. State that deletion is not guaranteed, including deletion-request-on-deletion-request limitations. |
| 6 | Interpret the NIP-18 `e` repost target and optional `p` author hint. Nonempty content is one original signed kind-1 event, not arbitrary plaintext. | 7 | Interpret `e`, `p`, optional `a` and `k` using NIP-25; the final `e`/`p` identify the target when multiple are present. Reference validation distinguishes a 32-byte hex event ID from a public key or event address. Full byte/string syntax, canonical numeric parsing and URI constraints are fixed in K01's implementation brief against the pinned protocol before code. They must not become an implicit regex chosen inside a renderer. Optional network evidence is bounded, separately supplied, verified and bound to the referenced ID; no real-time fetching is required for the first catalog.

## Required fixture families before implementation acceptance

For each kind: a minimal valid operation, complete complex operation, wrong type/missing member, duplicate/escaped object member, invalid known reference, unknown tag shown completely, suffix extension shown completely, aggregate-limit boundary and unrenderable input rejection. Include empty replaceable lists, unmarked/contradictory reply references, address identifiers containing colons, invalid repost evidence, multiple reaction references selecting the final target and omitted relay marker meaning read+write.

Independent fixtures establish canonical bytes and expected presentation roles. Hardware tests establish actual readability and physical input. Numeric limits and exact UI layout remain per-profile evidence; this candidate cannot qualify them by prose.
