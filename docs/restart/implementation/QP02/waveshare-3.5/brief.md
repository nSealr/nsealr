The maintainer reports SKU33360 with camera, battery and touch; received PCB/silicon/module markings and measurements remain unknown. Select ESP-IDF **v6.0.2**, peeled commit `7101770dc6db2667b3c477cc31365dd1acd6db4e`, as the future SDK baseline; vendor source lists it in the example matrix. Its tools manifest pins `riscv32-esp-elf esp-15.2.0_20251204` and the Linux-amd64 archive digest in the contract. No SDK/toolchain installation or version execution occurred. BSP requires IDF>=5.5 despite the example's older >=5.4 declaration. Under IDF6 the example selects `esp_video >=2.2,<3.0`; BSP/LVGL and other dependencies retain ranges. Therefore an exact Component Manager lock, source/archive closure, Python constraints and actual tool hashes must be frozen in a later build admission; this is not yet reproducible-build evidence.

The [revision contract](https://github.com/waveshareteam/ESP32-P4-WIFI6-Touch-LCD-3.5/blob/870588e62daaf723f3c52f0060d8dc053665ed30/docs/ci.md) distinguishes `rev1_3` for silicon `[1.0,2.0)` and `rev3_x` for `[3.0,4.0)`. No image is selected for the owned board until its silicon is authoritatively read. For v3.2, [Espressif AR2026-004](https://documentation.espressif.com/AR2026-004_Compatibility_Advisory_for_ESP32-P4_Chip_Revision_v3.2_EN.html) also requires a compatible esptool (>=5.3.dev3 on the6.x line) and documents the watchdog/32kHz fix in IDF>=6.0.1. IDF6.0.2 meets that source-version floor; its broad Python constraints do not prove the actual installed loader version. No eFuse or hardware state is assumed. The product documentation names P4NRW32X while the repository overview uses P4NRW32; neither spelling replaces an actual package/revision reading, and no suffix-to-silicon mapping is inferred.

Two implementation choices suffice. Direct Rust `esp-hal` supports P4 CPU/basic SPI/I2C, but its [current primary support matrix](https://docs.espressif.com/projects/rust/esp-hal/main/index.html) does not supply P4 MIPI-CSI, ISP or PPA drivers. A complete Rust camera pipeline is therefore an additional driver project, not the minimum probe. Choose maintained IDF/BSP peripheral code for capture/display/touch, retaining the **single existing Rust engine** for future Nostr parsing, identity, review and consuming authorization. This first probe contains no signing engine or custody. A later Rust/IDF target/ABI/allocator/owned-frame integration canary is still missing; no API, C approval boolean or second signer is admitted here.

Example09 configures OV5647 RAW10 1280×960 at45fps, requests RGB565 video, allocates two camera/two LCD buffers in PSRAM, center-crops and mirrors through PPA, then copies byte-swapped DMA stripes to LCD. Its preview is not complete QR intake or proof against clipping. Derived allocations are about5.53MB for those four RGB565 buffers plus a76,800-byte default internal stripe, before alignment, driver/LVGL/tasks and decoder memory. Actual `VIDIOC_QUERYBUF` lengths, negotiated format, heap margins and lifecycle/fault behavior remain measurements. [Source](https://github.com/waveshareteam/ESP32-P4-WIFI6-Touch-LCD-3.5/blob/870588e62daaf723f3c52f0060d8dc053665ed30/examples/esp-idf/09_video_lcd_display/main/main.c).

The BSP's80MHz setting is a **demo configuration**, not a qualified panel timing. Assuming sustained single-data-line SPI at that rate, RGB565 full frames alone imply at most `80,000,000/(320×480×16)=32.55fps`, before overhead. Neither45fps display nor any observed throughput is claimed. The exact received ST7796/module serial timing rating, permitted SCLK/duty/setup/hold at actual voltage and loaded bus, and sustained transfer/error behavior are missing; no new component research or timing change was made.
