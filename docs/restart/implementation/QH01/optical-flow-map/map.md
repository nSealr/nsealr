The fixed C ABI is a real shared-engine **33-frame historical host canary**, with callback Next/Approve/Reject, but no incoming-request API: it hardcodes kind0, request ID, known public fixture scalar 3, zero auxiliary bytes and fixture clock 0; Python's callback simulates approval. It returns a bare event through a 9216-byte caller buffer, not a transport-sized response. Its public key `f930…36f9` differs from the original optical fixture's `4f35…71aa`; it cannot serve that incoming request by relabelling its output. [F1–F5]

These are **source-data calculations**, confirmed against unchanged original byte files: `8 + ceil(4N/3)`, not optical measurements. The provisional static ceiling 704 is **decoded JSON bytes** (frame upper bound 947), while the worker's experimental 512 is **decoded QR-symbol output bytes**, i.e. the whole ASCII frame. Thus 452 fits the codec but its 611 frame is refused by that experiment. The existing animated response vector is 351/351/186 ASCII bytes (payload chunks 256/256/91); Bridge's static-only port cannot consume it. Animated caps 4096 decoded bytes/256 payload characters/64 frames, checksums and sequence/digest matching establish neither sender authority nor a framing choice. Effective method/transport/local intersections may be smaller; logical `parse_work`/retained-byte accounting is not image pixels, decoder CPU or measured heap. [C1–C5, W1]

The next justified software change is the **missing bounded, request-aware Pi↔shared-engine adapter**: preserve raw decoded JSON through core intake, bind local display/buttons to Rust-owned review, retain the key owner in Rust, supply trusted local clock/fallible auxiliary interfaces, and wrap the released event in the matching v2 response for real client verification. A known-public-identity engineering exchange must sign the actual incoming `sign_event`, not replay the canary or stop at get-public-key; it still supplies no real custody/provider qualification. Connecting the bounded image worker to actual capture and resolving full signed-response framing remain explicit dependencies, not permission to raise 512 or choose multipart now. Exact kit, image, ABI, operator and physical screen/camera measurements remain unidentified/pending. Pi capability conformance leaves signing providers unavailable. All five QH01 criteria and physical/release/provider gates remain open; no route/readiness is enabled here. [P9, G1]
