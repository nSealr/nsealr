# Nonce contract investigation — no amendment applied

**The e8 exact-byte expectation was wrong.** It paired the adapter's explicit zero32 auxiliary input with historical signatures whose nonce/auxiliary provenance was not established. Keep exact-byte testing, but derive the new adapter's expected signatures from the already pinned BIP340 reference with **the actual explicit auxiliary bytes**. Do not change the original fixtures, core, provider or e8 in this investigation.

The source chain is precise. `generate_fixtures.py:56` calls `schnorr_sign(digest,"",raw=True)`. The installed R00 Python binding forwards that digest unchanged and calls `secp256k1_schnorrsig_sign_custom(...,NULL)`. Both installed binding and embedded C ELF are byte-identical to R00's hash-pinned wheel 0.14.0; the extension does not dynamically load another libsecp256k1. The actual ELF's NULL branch XORs the key input with `ZERO_MASK`, not an unmasked key. Its 32 bytes at 0x25280 equal `tagged_hash("BIP0340/aux",zero32)` computed by the pinned S03 reference. Thus describing this R00 binary's NULL as “no auxiliary masking” would be false.

The authorized official PyPI sdist 0.14.0 is different: its primary C `nonce_function_bip340` bypasses auxiliary hashing/masking when data is NULL, then hashes key||publickey||message. Its sign_custom initializes noncefp/ndata to NULL. That explains a possible older nonce policy, **not the origin of these fixtures**. The sdist's derivation into the installed wheel/ELF is not demonstrated and its NULL branch differs. The 2021 sdist and 2026 wheel share a package-version label; that label is insufficient to identify embedded C source. No other release was investigated.

A02's frozen 26e6 diagnostic proves, for the two existing public basic/tagged messages, Rust==independent BIP340(zero32), legacy differs, and all signatures verify. Its separately frozen 4fd9 replay then calls the existing generator/binding with the matching actually loaded ELF: current generator==zero32 oracle==Rust, and !=legacy. These are peer-author executions, not new runs by this investigator. Historical legacy generation environment/nonce policy remains unknown; no vulnerability diagnosis or invented provenance follows.

The official pinned reference makes the distinction explicit: signing derives `t` from normalized secret XOR tagged_hash(aux32), whereas verification has no auxiliary-input parameter. A valid signature is therefore not, by itself, the exact signing oracle for a declared auxiliary value.

The necessary **later pre-code amendment** is narrow: bind the new basic/tagged expected signatures to the same raw event IDs, scalar 11×32, exact zero32 and unchanged S03 reference; retain exact event/canonical/request/key assertions and mutation rejections. Preserve legacy bytes as valid verification/interoperability goldens, without claiming their nonce source or requiring the new adapter to reproduce them. Do not replace equality by merely “signature verifies,” switch the provider to a legacy nonce path, or rewrite the original corpus. [Exact recommended values and source identities](conclusion.json) are proposals, not applied changes or runtime acceptance. e8 and all author failures remain unchanged; this is not an implementation review.
