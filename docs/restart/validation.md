## Corrections made by this review

1. **Remove implicit all-device gates.** S02/K01 close common semantics and scoped crypto/build feasibility. Physical stack/RAM, entropy, latency and transport tests close in V01, Q02/Q03 and V02/V03 for their own devices. The graph also checks that Pi/P4/no-SE releases do not acquire custom-fabrication ancestors and that Board SDK does not acquire Nostr application prerequisites.
2. **Make missing resources explicit.** Physical tasks now name kits, instruments, an operator and relevant independent reviewers/participants. Availability starts unknown; the machine executing Codex is not evidence that a physical bench exists. Preparation can proceed while procurement/access is resolved.
3. **Separate context from authority.** A browser origin label or host-forwarded RPC is not hardware-authenticated application identity. NIP-44 primitives are not complete NIP-17 messaging. [Client qualification](client-qualification.md) now states the intended tests and the cases that must fail closed.
4. **Move manufacturing constraints before routing.** Choose the relevant factory/service rules, stackup and test access before H06. Generic Board production/provisioning proof belongs in B03 independently of downstream Nostr production. Safe pilot signing/enrollment/recovery belongs before S05 admission, not only after the pilot.
5. **Scope CAD qualification to required operations.** Required native capture/validation/export can proceed without qualifying every optional MCP tool. A replacement Python binding does not inherit the previous environment's runtime results.

## Crypto feasibility and integration traps

The [reproducible isolated study](../../research/2026-10-13/crypto/README.md) compares `k256 0.14.0` and `secp256k1 0.33.1` using independent BIP-340 and NIP-44 conversation-key vectors. Both pass 19 BIP-340 verification cases, eight exact signing cases, and 35 valid/eight invalid conversation-key cases. It also probes `no_std` compilation and a freestanding final link for Cortex-M33 and the RISC-V instruction-set target used for P4 exploration. These artifacts are deliberately separate from the product firmware; full NIP-44 encryption/decryption is outside this experiment.

Two API mismatches need explicit regression tests: signing an already-computed Nostr event ID must not hash it again, and NIP-44 needs the raw ECDH x-coordinate rather than a generic hashed shared secret. A third failure appeared only at final link: the C and Rust RISC-V objects initially disagreed about floating-point ABI. Explicit matching C flags resolved the probe. Therefore `cargo check` or an rlib build is insufficient acceptance for a mixed-language device image.

These results support feasibility, not a final backend choice. Linked section size is not runtime peak RAM; a minimal entry symbol is not bootable firmware; no board was flashed. Production qualification still includes side-channel/blinding configuration, randomness failure, key lifetime/zeroization limits, resource budgets and review of the exact version/features. Do not rewrite mature cryptographic primitives to save a dependency.

## Hardware decisions that remain conditional

Start a bounded STM32U5 MCU probe and an independent single-SE qualification. **U585VI and SE051C2 are candidates, not a mandatory coupled pair or approved purchase/BOM.** Compare against documented requirements and the S3/alternative-SE probes; use H573 only for a demonstrated lifecycle need. Admit [U5A5VJ](https://www.st.com/en/microcontrollers-microprocessors/stm32u5a5vj.html) as a conditional internal-memory alternative if U585's measured budget fails, not a mandatory third port. Exact package variants and actual SE ordering/configuration identifiers matter. An evaluation board with a different package or supply option does not prove the final pinout.

For Nostr, do not promise a non-exportable identity merely because an SE supports ECC, ECDSA or Ed25519. BIP-340 requires its exact secp256k1 Schnorr operation; if the scalar must be unwrapped into MCU RAM for that operation, this exposure belongs in the threat model and physical test plan. Adding another chip does not automatically remove it. Trusted display/input also requires firmware, peripheral and DMA ownership; the SE cannot validate what a hostile screen shows.

SE051 maintenance introduces a distinct vendor-controlled applet authority. [NXP AN12907 Rev 1.2](https://www.nxp.com/docs/en/application-note/AN12907.pdf), sections 2–3, describes vendor-generated update scripts distributed to OEMs through EdgeLock 2GO; OEM delivery can be offline. Normal applet updates preserve objects/SCP keys, and robust rollback prevention also needs the documented SEMS key rotation. Owner control of the MCU firmware does not replace that authority. Mandatory API/errata/update documentation and developer access terms must be resolved before selection. An unavailable critical document is a reason to keep a selection open or reject a candidate, never permission to invent its behavior. A public alternative must meet the same required security properties; openness alone does not waive an applicable vulnerability.

Freeze electrical choices only after a per-pin and budget ledger: private SE buses, dedicated trusted display/input, protected maker expansion, voltage/current and power-off/backfeed behavior, USB-C current entitlement, charger/reset defaults, battery protection/thermal limits, debug/recovery and optional camera/NFC roles. “Many GPIOs” and a nominal display connector are not compatibility specifications. Optional peripherals can be modules where their use and isolation justify it.

H01 records document revision and reviewed sections; its inventory may close with declared SE-access gaps and a complete MCU subset. H02 measures the MCU, H02S tests the selected SE commands, and H03 measures power/display constraints. H04 requires closure of every mandatory selected-component document/erratum as well as those measurements. H05/H06 create and review the real native design; H07 prepares fabrication; H08/H09 validate identified assemblies. Paper calculations support a design decision but cannot close assembled-board acceptance.

Current manual availability is not complete: [RM0456 Rev 7](https://www.st.com/resource/en/reference_manual/rm0456-stm32u575585-armbased-32bit-mcus-stmicroelectronics.pdf) is the current U5 edition, while the archived full copy from which selected sections were reviewed is [official Rev 6](https://www.stmcu.jp/wp/wp-content/uploads/2021/07/RM0456_Rev6.pdf). The relevant revision delta remains open. Restricted SE051 API/errata access also remains open. These gaps prohibit a final part/register-level sign-off.

The [official ST pin data](https://github.com/STMicroelectronics/STM32_open_pin_data/tree/7d1f1514ed5583ec5007ad91236b4e1d377295b1) supports a preliminary 69-pad U585VI/VIQ allocation for the broad interface hypothesis, leaving 12/9 GPIO after an additional PC13 erratum reservation. One concrete conflict is I2C2 SDA versus UCPD dead-battery use on PB14; the witness uses I2C4. This checks pad/signal existence, not electrical behavior, DMA isolation or routing. A 240×320 RGB565 framebuffer consumes 150 KiB; two QVGA RGB camera buffers plus that display and an assumed 200 KiB working set total 650 KiB. Against approximately 720 KiB usable main SRAM with the optional ECC configuration enabled (only 320 KiB of main SRAM is ECC-protected), this is tight enough to require measurement, tiling or a different part. These are assumptions and arithmetic, not measured firmware RAM or a frozen display/camera requirement.

## CAD and production evidence

The previous KiCad 10.0.7 canary remains valid only for its recorded environment and operations. The KiPilot vendored Python wheel had generated protobuf code requiring a runtime incompatible with its declared dependency range. On October 18 a new normal installation with official `kicad-python 0.8.0`, `protobuf 5.29.6`, MCP 1.30.0 and KiPilot `303e62010172bf99c2aa41c10237c18bcabcca7a` passed dependency checks and the bounded runtime canary against KiCad 10.0.7. The installed binding files match the official wheel; no dependency bypass was used.

Actual stdio MCP checks covered board summary, footprints, pads, text, text update and save: disabled-mutation rejection, a no-change dry run, stale-text rejection, persisted edit after editor restart, restoration and a second restart check. Native intentional bad ERC/DRC failed, corrected checks passed, and independent connectivity assertions plus Gerber/drill/BOM/placement exports passed for a three-component, seven-pad, three-net, thirteen-track canary. This qualifies those operations only. Fresh-process imports of optional `board_jobs`, `board_rules`, `schematic` and `schematic_types` still fail; 135 advertised tools are not 135 qualified tools. See the [PCB development contract](pcb-development.md) for the operation and physical-gate boundaries.

Official [KiCad IPC documentation](https://dev-docs.kicad.org/en/apis-and-binding/ipc-api/for-addon-developers/) distinguishes stable GUI/PCB support from KiCad 11 development features. [Protobuf's runtime policy](https://protobuf.dev/support/cross-version-runtime-guarantee/) explains why ignoring the version conflict is not a repair. E01 retains a native CLI/source-generation fallback and enables only demonstrated calls.

For manufacturing, select the actual supplier rules rather than a generic “DRC clean” label. For example, [Eurocircuits' assembly preparation](https://www.eurocircuits.com/technical-guidelines/assembly-manufacturing-technology/front-end-data-preparation/) and [JLCPCB's placement-file requirements](https://jlcpcb.com/help/article/pick-place-file-for-pcb-assembly) establish concrete footprint/orientation/BOM/CPL checks. These are candidate service requirements, not a factory selection or compliance claim. DVT, production-intent testing, controlled provisioning and per-unit traceability remain distinct gates.

## Lean execution and stop conditions

Run `python3 scripts/validate_restart_plan.py` or `make test`. The validator checks graph/status/resource consistency, forbidden release ancestors and exact-candidate review/evidence records for closed tasks. Its negative tests cover false readiness and altered evidence. It does not audit a reviewer, inspect a physical device or decide whether a security argument is correct.

Use one coordinator and at most the available specialist slots, one writer per scope/CAD session and a separate exact-candidate reviewer. Begin the seven ready tasks; collect hardware sources alongside P01 and close H01 only after its prerequisite. Work on physical paths starts when the named resources exist. Do not start a separate orchestration service.

Stop a candidate selection on an unmet required guarantee, unavailable mandatory command/document, unbounded hostile-input path, impossible recovery promise or resource/pin conflict. Stop a pilot on an unexplained signature, identity change, key loss or bypass of a required boundary. Preserve failed experiments. A design revision invalidates affected evidence and triggers scoped requalification, not a graph cycle or a reset of unrelated products.

No calendar completion or adoption promise is justified yet. First establish repeatable software baselines and the physical request/review/sign/verify slice; then estimate from measured throughput, supplier lead times, review availability and observed rework. The first useful release is the first profile that passes its own gates.
